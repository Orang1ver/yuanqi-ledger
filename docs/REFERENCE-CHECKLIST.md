# 数值待核清单（P8）

> 这是「食物库的数字准不准」的**待办台账**，不是结论。
> 起因：有人问「15 个饺子怎么算出 1860mg 钠的」——算术没错（15 × 20g = 300g，
> 300g × 620mg/100g = 1860mg），但**那两个数都没有可复核的来路**。
>
> 复现方式：见文末「怎么重新扫一遍」。

## B. 份量口径没写清（95 条）

### ✅ 已在 0.7.1 修掉：干重食物被按熟重算

> 修的是**口径**（克数算错了）；这些食物的**数值本身**仍待核 —— 那是第 4 步的事。

| | 值 | 口径 |
|---|---|---|
| 库里「挂面」 | 346 kcal / 100g | **干重** |
| 份量表 `碗[面条]` | 一碗 250g | **没写生熟** |

「挂面」的别名含「面条」（`干面条`），所以「一碗挂面」会命中 `碗[面条] = 250g`。
**实测（`npm run probe`）**：

```
✓ 「一碗挂面」 → 挂面  (库 id: noodles-dry)
    折算：1 × 「一碗」250g = 250g（常见 150~350g）
    本条：865.0 kcal · 蛋白 26.3g · 脂肪 2.3g · 碳水 185.3g · 钠 425mg

✓ 「一碗面」 → 面条  (库 id: noodles-cooked)
    本条：275.0 kcal   ← 这条是对的
```

**高估 3 倍**，而且它拿的是「干重」的数去乘「一碗」—— 碗里装的从来不是干面。

排查时发现**同一个错在库里躺着三条**，不止挂面：

| 食物 | 修复前 | 修复后 |
|---|---|---|
| 挂面（`noodles-dry`） | 865 kcal | **277 kcal** |
| 粉丝（干）（`vermicelli-dry`） | 845 kcal | **270 kcal** |
| 米粉（干）（`rice-noodle-dry`） | 865 kcal | **277 kcal** |

实际修法：在通用规则**前面**插一条按干重给克数的专门规则
（`碗[…] = 80g` / `份[…] = 80g`，note 写明「按干重算」）——
份量表是**先命中先赢**，位置比内容更容易出错。
并加了闸门 ④c（`check:nutrition`）：干重食物的每条命中规则，note 必须写明是干重口径。

### ✅ 也在 0.7.1 修掉了：「下了一碗挂面」会丢份量

```
✓ 「下了一碗挂面」 → 挂面
    折算：没写份量，按分类兜底 200g = 200g（估算）  ⚠ 估算
```

`LEAD_NOISE` 里有「吃了 / 喝了 / 点了 / 买了」，**没有「下了」「煮了」** ——
于是整句当成食物名去模糊检索，配到了挂面，但**份量和单位一起丢了**，退化成分类兜底的估算值。
与 0.6.1 修的「昨晚」是同一类（地雷 19 的同类：看起来对、数字错）。

实际修法：`LEAD_NOISE` 补了 `下了 / 煮了 / 做了 / 炒了 / 煎了 / 烤了`。
⚠️ 只加**动词**，没加「下了碗」这类 —— 噪音表里带量词就会顺手把量词剥掉，重犯地雷 19。
现在「下了一碗挂面」→ 80g → **277 kcal**。

### 其余口径未写的（按量词归类）

| 量词 | 条数（约） | 典型条目 | 风险 |
|---|---|---|---|
| 份 / 盘 / 碗 | 40+ | 白粥、小米粥、面条、米线、玉米、红薯、紫薯、土豆、米粉（干）、红薯粥 | 粥/面/蒸薯类的"一碗/一份"**生熟差异明显** |
| 个 | 20+ | （多为水果，风险较低） | 可食部是否含皮/核 |
| 包 / 袋 / 盒 / 瓶 | 20+ | 零食饮品类 | 一般已带 note，风险较低 |
| 把 / 串 / 块 | 10+ | 花生（炒）、瓜子（炒） | 低 |

**真正要紧的是第一行**：`碗 / 份 / 盘` 配「煮/蒸/干」类食物。
`碗[米饭]=180g` 已经写了「指熟重」，是个好例子 —— 其余照它补即可。

> ⚠️ **口径更正（0.7.3）**：上面那个「40+」高估了一个数量级。
> 真正缺 `note` 的规则只有 **4 条**（`碗[粥,汤]`、`碗[饺子,馄饨,云吞]`、
> `份[饺子,馄饨,云吞]`、`盘[时蔬,青菜,…]`）。
>
> 差在哪：这张表数的是**食物条数**，而 `note` 是**规则级**的 ——
> 一条规则被十几条食物命中就会被重复计数。
> 更要紧的是得按**运行时的口径**算：一条规则虽然"提到了"某个食物，
> 但它排在更靠前的规则后面时**永远走不到** ——
> `碗[粥,汤]` 的 match 里有个单字「汤」，「面条」的别名「清汤面」也算命中它，
> 可面条规则排在前面。拿"哪条规则提到了它"去数，就会给一条死规则补说明、
> 而真正的缺口漏掉。闸门 ④d 用的就是「真正生效的那条规则」这个口径。

## C. 其余无出处条目（184 − 上表）

按分类汇总，不逐条列：

| 分类 | 条数 |
|---|---|
| （全部） | 184 |

这些的处理方式不是"逐条找权威值"，而是**分两步**：

1. **能被官方平台覆盖的** → 按 `data/foodSources.json` 的格式补引用（0.6.0/0.6.1 已经这么做了 39 条）；
2. **官方平台没有的**（如饺子、馄饨、成品菜） → 走 P6.1 第二批的**按配方估算**：
   列原料 → 查表 → 折算熟重（生熟比）→ 出油率 → 加权和，
   `source` 写成「按配方估算（参照《中国食物成分表》）」，并**在份量表里写明生熟口径**。

## 怎么重新扫一遍

本次扫描用的是一次性脚本（已删），逻辑是：

1. `data/foods.zh.json` 里 `source` **不含**「中国食物成分表」的 → 无出处；
2. 对每条食物，用与运行时相同的子串规则（`match.some(m => names.some(n => n.includes(m)))`）
   找出它命中的份量规则；这些规则的所有档位里**一个 `note` 都没有**的 → 口径未写；
3. 重点嫌疑：`source` 带「煮/蒸/干/炒/油炸/烤/煎」字样，或名字属米面类。

> 这份扫描**没有进仓库**（它是一次性的）。要做成常驻闸门的话，
> 应该并入 `scripts/check-nutrition.mjs` 的「份量表联动」那一节 —— 见下。

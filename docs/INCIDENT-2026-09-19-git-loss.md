# 事故报告：合并分支时 `.git` 被批量移入回收站

- **发生时间**：2026-09-19 19:10:33 – 19:10:47（约 14 秒内）
- **影响面**：本机开发仓库（`C:\Users\StarRiver\Desktop\code\yuanqi-ledger`），**不涉及线上站点与用户数据**
- **最终损失**：**零**。全部 1169 个 git 对象被定向找回，`git fsck` 无 missing/broken，提交历史完整
- **险些损失**：当时**有一批只存在于本地、尚未推送的提交**（`verify-ota-rollback` 分支的
  `3ce2ef8` / `1ee3164`，即回滚保险三臂对照验证的全部成果）。若恢复失败，这部分工作会真的没有
- **等级**：本地仓库级事故。**没有造成实际丢失，但离丢失只差一次「打不开 `.git` 就放弃」**

## 2. 现象

1. **仓库"消失"**：git 判定"是不是仓库"要求 `HEAD` + `objects` + `refs` 三者齐全。
   `refs/` 整棵被移走后，即使 `HEAD` 文件还在，git 也直接不认这个仓库。
2. **对象库被掏空**：`objects/` 下 76 个分片目录**全部为空**，`count-objects` 报 `count: 0`。
3. **pack 只剩索引**：`objects/pack/*.idx` 还在，但配对的 `.pack` 文件没了，
   git 报 `no corresponding .pack`。
4. **同时出现的第二处异常**：`git status` 冒出一批 ` D` 条目 —— `scripts/` 下 **17 个文件整个消失**。
   经对照实验确认这是**另一个独立问题**：`git checkout <分支>` 在本机会删文件，可稳定复现两次。
5. **去向往回收站**：解析回收站 `$I` 元数据后确认，19:10:33–19:10:47 共有 **1062 个 `.git` 下的文件**
   被移入回收站，其中包括 `objects\5a\db7570…`（正是 `main` 的提交对象）。

---

## 3. 根因分析

### 3.1 直接触发链

```
工作区有 13 个文件「stat 抖动」（scripts/ 下，内容与 HEAD 完全一致，只是换行形态是 CRLF）
        ↓
git merge 认为工作区脏，按惯例先 stash
        ↓
stash 失败（fatal: stash failed）
        ↓
紧接着 .git 下 1000+ 文件被批量移入回收站，refs/ 与 objects/ 内容一并消失
```

**关键前置条件**：这台机器 `core.autocrlf=true`（检出时把文本文件换成 CRLF），
而索引/对象库里是 LF。两者**内容语义相同、字节不同**，于是 git 反复判定"这些文件被改过"，
却比对不出实质差异 —— 这就是那 13 个文件的"stat 抖动"。

### 3.2 ⚠️ 未能坐实的一环（如实标注）

**"是谁发起了那 1000 多次删除"没有被坐实。**

- 本机运行环境里有一层"批量删除守卫"（`node-safe-delete-shim`），它会拦截一次性的批量删除。
- 但守卫状态文件在 19:10 那一轮**只记录了一条 `count=1`**，说明这 1000 多次删除
  **不是走 shim 的 `rm` 路径**发起的，更像是回收站 Shell API 一类的删除。
- 因此**不能断言"是 git 自己删的"**，也不能断言是宿主工具所为。**结论停在"未坐实"，不编圆。**

### 3.3 为什么危险

- 事故发生时，`verify-ota-rollback` 的成果**尚未推送**。本地 `.git` 一旦不可恢复，
  这批提交将没有任何副本 —— 这正是"差点白干一下午"的实质。
- 损坏形态具有**欺骗性**：`.git/HEAD` 还能读、`objects/pack/*.idx` 还在，
  粗看像是"只是索引坏了"，容易让人误以为跑一句 `git reset` 就能好，从而错失回收站里的原始文件。

## 4. 恢复过程（零损失）

1. **先封存，再动手**：`cp -r .git <仓库外>` 保存损坏现场，避免后续操作二次破坏。
2. **定位真实去向**：解析回收站的 `$I` 元数据（时间戳在偏移 `16..24`，大小在 `24..28`，
   原路径从偏移 `28` 起是 UTF-16LE；`$R` + 同一个 6 字符 ID 即文件内容）。
3. **定向捞回对象**：按元数据把 `objects/` 下的文件复制回原位，**只补「目标不存在」的，不覆盖**，
   共恢复 **1169 个文件**。
4. **单独校验 pack**：`pack-2924a61e….pack`（213,173 字节）魔数为 `PACK`，
   文件末尾 sha1 自校验与文件名一致 → 确认文件完整（此前 `count: 0` 是因为它整个被移走了）。
5. **手写 refs** 并逐个核对取值：`main` = `5adb757`、`verify-ota-rollback` = `1ee3164`、
   `docs-truth-fixes` = `3784786` ✓
6. **对象图自证**：`git fsck` **无 missing / broken**。

**结论：对象图完整恢复，一条提交都没丢。**

## 6. 今后开发注意事项

### 6.1 动手前

1. **`cp -r .git <仓库外的路径>` 先备份**。`.git` 只有十几 MB，比任何恢复流程都便宜。
2. 确认工作区是干净的；若 `git status` 里出现**内容没变却显示被修改**的文件（CRLF 形态差异、
   stat 抖动），**先处理这种状态，别直接开始合并** —— 它是本次事故的前置条件。

### 6.2 操作时（本机硬规矩）

3. **分支名一律用扁平分名**（如 `fix-exercise-sort`）。本机建带斜杠的分支名会**静默失败**：
   退出码 0、但 ref 根本不存在 → 之后的提交变成无父的孤儿提交、与 `main` 断链且不报错。
   建完用 `git show-ref refs/heads/<名>` 自证。
4. **不要用 `git checkout <分支>` 切分支** —— 本机实测会把 `scripts/` 下整个目录删掉。
   只想看别处的内容，用 `git show <ref>:<path>`。
5. **合并走管道，不用 `git merge`**：

   ```bash
   git merge-tree --write-tree <A> <B>          # 得到合并后的树
   git commit-tree <tree> -p <A> -p <B> -F <msg>  # 造出双父提交
   git update-ref refs/heads/main <new>          # 移动分支
   git cat-file blob <new>:<path> > <path>       # 把文件写回工作区
   git read-tree <new>                           # 刷新索引
   ```

   完成后用 `git diff` / `git diff --cached` / `git status` **三者皆空**来自证。
6. **永不 `git add -A`** —— 只 add 本次真正改动的文件。
7. **`git update-ref` 写完必须 `git rev-parse` 复核**。本机出现过三次"退出码 0 但值没变"。

### 6.3 收尾时

8. **重要提交尽早推送**。事故发生时那批成果只在本地，是风险的全部来源 ——
   凡是"一下午的活"，别攒着不推。
9. 定期 `git fsck` 看对象图是否完整；发现 `.git` 异常**先封存副本再动手**。
10. **绝不一键还原回收站**。事故现场在回收站里的副本是恢复的依据，
    整体还原会把无关的垃圾一起撒回来，并覆盖已经修好的状态。要恢复就**按 `$I` 元数据定向捞**。

### 6.4 判断"是不是真坏了"

11. `fatal: not a git repository` 但 `HEAD` 可读 → **先按"三要素缺失"排查**
    （`HEAD` + `objects` + `refs` 是否齐全），而不是急着重装或重新 clone。
12. 只要对象文件还在（哪怕在回收站里），**历史就还能救回来** —— 先别做任何写操作。

## 7. 一句话总结

**这次没有丢东西，是因为出事前的一批提交恰好还能从回收站里按元数据捞回来，而不是因为流程足够安全。**
真正的教训是：本地这份 `.git` 没有任何冗余，所以"动手前备份 + 不用会静默删文件的命令 + 及时推送"
这三件事必须成为习惯，不能靠运气。

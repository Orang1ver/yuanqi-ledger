# 元气账本

记录每天的**吃、喝、动、睡**，看清自己的健康状况。

一个**纯前端**的个人健康账本：数据全部存在你自己的浏览器里，没有服务端、没有数据库、
没有账号体系，AI 由浏览器直连。构建产物是静态站点，可以丢到任何静态托管上。

---

## 功能

| 模块 | 内容 |
|---|---|
| 今天 | 喝水（按你的杯子换算）、步数、睡眠、心情、体重、运动，一屏记完；**「今天吃什么」从你的菜单库里挑一道**（不用先记账、不填 Key、断网也能用，挑好了点「就吃这个」直接记进饮食日记）；「今天还该吃点啥」按当天缺口给建议，填了 DeepSeek Key 还能「✨ 帮我挑」 |
| 饮食 | 说一句「晚上一包薯片，一杯奶茶」就记完；当天热量环、营养素对目标的比对、饮食质量分、一条该改的建议 |
| 健康小屋 | 健康档案（身高体重年龄活动量目标）→ 自动推导热量/喝水/步数目标、BMI 与健康体重区间 |
| 成就 | 打卡徽章（连续达标）与运动里程碑（累计次数/里程），两套独立命名空间 |
| 菜单库 | 你常点的店与菜；支持改商家名、批量删除、一次撤销；菜品可按菜名估出热量区间，或关联到食物库里的某条食物 |
| 周报 | 一周打卡达标率、饮食质量（含与上周对比）、运动统计、体重变化 |

内置 **223 条中式食物库**与 **111 条份量换算规则**：写"一包薯片"、"一杯奶茶"能折成克数、
热量与钠含量，每个数字都能追到"哪条食物 × 多少克"。

基础食材（蔬菜 / 菌菇 / 基础肉）的数值取自
[中国疾控中心营养与健康所《中国食物成分表》查询平台](https://nlc.chinanutri.cn)
（该站声明数据仅限**非商业**使用），每条 `source` 里带网页编号；
`data/foodSources.json` 是引用台账，`npm run check:reference` 保证"写了来源的条目都有据可查"。

三条贯穿饮食模块的规矩，写在界面上也写在测试里：

- **数字只有一条来路** —— 查食物库再乘一次克数。模型只负责听懂与措辞，不吐任何数值。
  「帮我挑」是这条规矩最吃劲的地方：模型只能回"菜单里的第几道"，
  屏幕上的热量仍然由本地 `estimateDish` 现算，它措辞里的数字会被直接摘掉。
- **「没有数据」≠「0」** —— 钠 / 纤维查不到时保持"未知"并单独报覆盖率，
  绝不悄悄按 0 计入，否则"今天钠 550mg"会是个假结论。
- **估不出来就不给数字** —— 菜单里拆不干净的菜名会直说估不出来，
  而不是给一个看起来精确的错数。

**规划中**：条码扫描、菜单库词表扩容、睡眠/心情的深入分析等。
完整路线图见 `docs/ROADMAP.md`；已实现的「帮我挑」方案记录见 `docs/HANDOFF-AI-RECOMMEND.md`。

## 技术栈

Next.js 16（App Router）· TypeScript 5 · Tailwind CSS 4 · `motion` · `canvas-confetti`
· 静态导出（`output: "export"`）· PWA（含 iOS 启动图与安全区适配）

**没有后端。** 所有数据在 `localStorage`，所有计算在浏览器里完成。

## 构建与部署

部署在子路径下时必须注入 `BASE_PATH`，否则所有资源路径都会错：

```bash
MSYS_NO_PATHCONV=1 BASE_PATH=/yuanqi-ledger npm run build     # 产物在 out/
```

发布（一键：校验版本 → 构建 → 注入 SW 版本号 → 推 gh-pages → 打 tag）：

```bash
node scripts/deploy.mjs
```

> 本机连不上 github.com（DNS 被挡、需靠 hosts 重定向时），用两个环境变量把差异带进来，
> 不动仓库配置：`DEPLOY_REMOTE_URL`（远端 URL，可含凭据）、
> `DEPLOY_GIT_CONFIG`（空格分隔的 `-c key=value`）。详见 `scripts/deploy.mjs` 头部注释。

### 部署到子路径后的自检

只测路由地址是不够的 —— 曾经因为原生 `<a>` 漏了 `basePath`，直接访问路由是 200、
**点击却 404**，那种测法测不出来：

```bash
node scripts/preview.mjs --port 4177          # 把 out/ 挂在 /yuanqi-ledger 下
python scripts/verify-subpath.py              # 静态分析产物里的每条站内链接
python scripts/verify-subpath.py --http http://127.0.0.1:4177   # 附加真实请求探测
```

> 忘了带 `BASE_PATH` 构建时，产物里所有路径都是根相对的，检查会刷屏报错 ——
> 但那全是误报，根因在构建命令。脚本会先探测这一点并直接告诉你，别急着改代码。

## 打安卓包（APK）

网页那一半本来就是完整的 PWA；安卓包只是**一层壳**（Capacitor 把静态产物装进 WebView），
没有加任何功能，也没有让数据离开手机。

```bash
npm run android:apk        # = scripts/android/build-apk.ps1
```

它按顺序做四件事，做完把包放到 `dist/yuanqi-ledger-<版本>.apk`：

1. **不带 `BASE_PATH` 构建**（`out/`），并断言产物里没有 `/yuanqi-ledger/` 前缀
2. 把 `sw.js` 的版本占位符注入真版本号（与 `scripts/deploy.mjs` 同一套）
3. `npx cap sync android` 把 `out/` 铺进 `android/app/src/main/assets/public`
4. `gradlew assembleRelease`，然后用 `aapt2` / `apksigner` 验包名、版本、签名

装到手机：

```bash
adb install -r dist/yuanqi-ledger-0.13.0.apk
```

**换机器/重装时先铺工具链**（本机已装好，装在 D 盘）：

```bash
powershell -ExecutionPolicy Bypass -File scripts/android/setup-sdk.ps1
```

### 三个容易白忙一场的点

- **打包时构建绝不能带 `BASE_PATH`**。子路径是给 GitHub Pages 的，而 WebView 从
  `https://localhost` 起、站点根就是 `/`。带上子路径的表现是**页面能开、`_next/` 全 404
  —— 也就是纯白屏**，而包里看不出任何异常。上面的脚本会替你断言这一点。
- **签名密钥不在仓库里**。它在 `D:\Android\keystore\yuanqi-release.jks`，
  由 `android/keystore.properties`（gitignored）指过去。没有它 Gradle 一样会"成功"，
  只是产出一个**装不上的未签名包**。所以脚本先断言密钥在，再用 `apksigner` 验一遍。
  ⚠️ **这个 jks 和它的密码要自己备份** —— 丢了就没法给已装的 App 做原地更新。
- **图标要单独重铺**。`cap sync` 只管 `assets/public`，不会动 `android/app/src/main/res/`。
  改了主题色或 `scripts/make-icons.py` 之后，先 `npm run icons` 再打包。

### 发版顺序（**先打包装包，再发布**）

```bash
npm run android:apk        # 1) 打出 dist/yuanqi-ledger-<版本>.apk
node scripts/deploy.mjs    # 2) 发布网页版 + version.json + 把安装包放到站点上
```

第 2 步会把安装包放到站点的 `/apk/` 下，并写一份 **`version.json`**：

```json
{ "version": "1.1.0", "apk": "apk/yuanqi-ledger-1.1.0.apk", "site": "https://orang1ver.github.io/yuanqi-ledger" }
```

**这份文件就是「应用内更新」的接口** —— 网页版和安卓 App 都来问它"最新是哪个版本"。
顺序反了的话网页版照样能更新，但**安卓 App 收不到更新提示**（脚本会警告一句，别忽略）。

### 应用内更新是怎么工作的

两边的更新方式**根本不同**，这不是实现偷懒，是平台就这样：

| | 网页版 | 安卓 App |
|---|---|---|
| 资源在哪 | 服务器上 | **打包在安装包里** |
| 提示什么 | 「发现新版本 v1.1.0，刷新即可用上」 | 「有新版本 v1.1.0，下载新的安装包就能用上」 |
| 点了做什么 | 清掉离线缓存 + 重新进入 | 跳浏览器下载新包，点开装一次 |
| 数据 | 不动（数据在 localStorage） | 不动（同一个包名与签名，覆盖安装） |

- 检查时机三个：打开、从后台回到前台、网络恢复。
- **壳里必须知道线上站点的绝对地址**：`location.origin` 在壳里是 `https://localhost`，
  拿它去拼"哪里能下到新包"是下不动的（见 `lib/update.ts` 的 `REMOTE_SITE`）。
- ⚠️ 安卓**不允许** App 给自己静默升级（除非走应用商店的更新接口），
  所以这一步必须用户点一下 —— 不是没做完。
- 「稍后」记的是**版本号**，只对那一个版本生效；下一个版本照样提示。

> iOS 那边**不需要另做一个包**：这个 App 在 iPhone 上就是"添加到主屏幕"的 PWA，
> 安装引导与更新机制都是现成的（见 `IOSInstallHint.tsx` 与 `public/sw.js`）。
> 要上 App Store 得有一台 Mac + Xcode，那是另一件事。

### 启动动画

冷启动时盖一层品牌遮罩（环自己画出来 + 品牌名淡入，约 0.4 秒后淡出），
它**在服务端渲染的 HTML 里** —— 盖住的正是"HTML 到了、React 还没水合"那段白屏。
三个出口：正常收掉 / **点一下立刻跳过** / 4 秒硬兜底（React 万一没起来）。
与安卓启动图同形状，且尊重系统的"减弱动效"设置。

## 五道闸门

改了数据层、界面或食物库之后，跑这几个就知道有没有把东西弄坏：

```bash
npm run check:data       # 把既有结构的数据喂进数据层，看读不读得出来
npm run smoke            # 真实浏览器打开产物，确认屏幕上真的显示出了这些数据
npm run check:nutrition  # 食物库质检：闭合校验、物理上限、重名、体积预算、份量覆盖
npm run check:reference  # 引用台账：每条标了外部来源的数值都要有据可查
npm test                 # 营养层与数据层单测
```

**`check:data`** 验的是**数据层**：18 个 localStorage 键、字段名、嵌套结构。
它编译 `lib/` 并由 Node 直接调用里面的真实读写函数（不是复制一份逻辑），
所以验的就是产品会跑的那段代码。自证它真的会拦人：

```bash
YQ_SELFTEST=1 npm run check:data      # 故意删掉健康档案，必须报错退出
```

**`smoke`** 验的是**界面**：数据层读得出来，不代表画得到屏幕上 —— 中间还隔着
hydration、日期上下文、卡片订阅。它用本机 Edge 的调试协议打开构建产物、
写入数据、读回屏幕上的文字和输入框的值，并截图到 `.tmp-smoke/`。
刻意不引入 Playwright（不必为跑一次冒烟下一个 500MB 的 Chromium）。
加 `--data <备份文件>` 可以让它改吃一份备份文件，于是**你正要交给别人的那个文件**
本身也能被验一遍，而不是拿一份"等价的"代理样本去猜。

它的断言词是**从被注入的数据里挑出来的**：先读一遍 `app/` 的源码，
只保留界面上本来**找不到**的名字（`米饭`、`奶茶` 这类写在搜索框 placeholder 里的词会被排除），
「屏幕上出现的这个词只可能来自数据」才是真的被验证了。
饮食页分两种情况断言：样本里没有 `recipe.dietLog.v1` 这个键（老用户升级后就是这样）
→ 必须显示空状态；喂样例备份 → 记录里的食物名必须真的画出来。

前置：先带 `BASE_PATH` 构建一次（`npm run smoke` 会自己按需拉起预览服务）。
两个脚本的样本数据是**同一份** `scripts/fixtures/legacy-v1.json`，不会各写一套而漂移。

它还会**定向查一个只能靠"时间"看出来的 bug**：喝水进度环的「第一次点击就该有动画」。
静态截图对这类问题毫无用处（首次挂载时元素已经处于最终值，截图上和"动画播完了"一模一样），
所以判据是两条结构性的事：进度为 0 时那根弧线**必须已经在 DOM 里**，
且点一下之后连采样必须**采到中间值**（只有首尾两值 = 一步跳过去了）。
前置状态由检查自己造（先一路减到 0），不假设样本数据 —— 样例备份里"今天"的水本来是满的，
靠假设会误报。把 `ProgressRing` 改回旧写法，这条检查会以「弧线元素只有 1 个」的名义变红。

它还定向查另外五条只能靠交互看出来的事：**餐次**是不是真落到选中的那一餐
（不能靠"按时间猜"恰好猜对）、**「一顿饭」预设**是不是真的一次落多条、
**份量档位**点了之后克数是不是真的变了（而且要**换个档位**点，点默认那个测不出东西）、
**周报的睡眠**在一条记录都没有时会不会显示成「睡了 0 小时」
（这条的前置要精心造：把睡眠**和**心情一起抹掉，卡片会走空态、`null` 与 `0` 的区别根本露不出来）、
以及**「帮我挑」**——最后这条会拦下一次假的模型返回，验四件事：
没填 Key 时按钮不显示、请求确实发出去了并带着设置里的 Key、
**模型编的菜单外的菜不许上屏**、**模型嘴里的数字不许上屏**（屏幕上那份热量必须来自本地估算）。
每一条都逐条破坏实现自证过会变红。

**`check:nutrition`** 验的是**食物库本身**。它只读 JSON、不编译，所以数据坏了第一道就拦住。
最有价值的一条是**闭合校验**：`蛋白×4 + 脂肪×9 + 碳水×4` 必须约等于标称热量 ——
食物库最容易犯的错就是数字看着像那么回事、比例却自相矛盾（黄油能"100 克里含 98 克脂肪
再加 0.9 克碳水、热量还 888"），这种错只有算一遍才会现形。

还有一条**份量表联动**：每条食物至少要有一条份量规则命中它。命中不了的话，用户写
「一份草莓」时查不到这个组合，会**静默**退化成按分类兜底的估算克数 ——
界面上照样出一个数字，只是那个数字没有依据、用户也看不出来。补上这条检查时，
它一口气列出了 19 条"有名字、有营养值、但没有份量规则"的食物。
自证它真的会拦人（两处破坏各喂给一条检查）：

```bash
YQ_SELFTEST=1 npm run check:nutrition    # 改坏薯片脂肪 + 塞一条没有份量规则的食物，两条都必须报错
```

只有算术与结构错误能被这条闸门抓住，**它证明不了数值全对** ——
数值本身错但比例自洽的情况（比如把某种菜的钠记成了 1/10），要靠下一道闸门人工校核。

**`check:reference`** 验的是**数值的来路**。它拿 `data/foodSources.json` 与食物库对一遍：
凡是 `source` 里写了外部权威来源的条目，都必须在台账里登记过；反过来，台账里的每一条
也要在 `source` 里写明 —— 两边不许单边存在。自证：

```bash
YQ_SELFTEST=1 npm run check:reference    # 删掉一条登记，必须报错退出
```

⚠️ 台账**只记引用标识**（哪个库、第几号页面、什么时候取的），**不复制表格数值** ——
一是版权，二是本仓库既有的约定（参照集不进仓库）。
所以它保证的是"每条都有据可查、出处没写错"，**不是"数值一定对"**；要核对就按编号回官网查。

**`test`** 验的是**营养层与数据层的语义**，也就是那些"算错了也不报错、但结果就是错的"规则：

- **"没有数据" ≠ "0"** —— 库里查不到的钠保持 `undefined`，求和时单独报覆盖率，
  绝不悄悄按 0 计入（否则"今天钠摄入 550mg"可能是假的）
- **快照语义** —— 记录里存的是写入那一刻的营养值，事后改食物库不会改写历史记录
- **数字只能来自一次乘法** —— 端到端断言所有营养数字都等于 `nutritionOf(食物, 克数)`，
  从结构上保证模型给的数值混不进来
- **今天还没吃完时不说"营养不够"** —— 不足型问题必须等当天热量到目标的 60% 才报
- **没记录的那天不进平均** —— 一周只记两天就算两天，不按 7 天摊（否则分数跟着记录习惯走）
- **估不出来就不给数字** —— 菜单里拆不干净的菜名必须拒绝估算，而不是给个够不着的区间

想手动看一条口语输入是怎么算出来的：

```bash
npm run probe -- --text "晚上吃了一包薯片，一杯奶茶"
```

它会打出逐项来源（食物 id、折算依据、数据出处）与相对参考目标的位置。
探针只为"看得见中间过程"，不参与验收。

想空着手看看界面长什么样（新装的站是空的，看不出兼容性）：

```bash
npm run demo:data     # 生成一份日期锚定今天的样例数据备份，导进去四个页面就都是活的
```

## 数据与备份

你的全部记录都存在**这台设备的浏览器**里。以下操作会让数据消失：

- 清除浏览器数据 / 缓存
- 换手机、换浏览器
- 换域名或换部署路径（同域名下换路径**不会**丢，localStorage 是按域名隔离的，与路径无关）
- 把应用打包成原生 App（WebView 是另一套存储，必须重新导入备份）

所以在换设备前，请到 **设置 → 数据备份 → 导出备份** 存一份 JSON。

### 迁移既有数据

如果你手里有更早版本导出的备份 JSON：

- 如果新站与原站**同域名**（例如都在 `orang1ver.github.io` 下）→ 打开即见原有数据，无需操作
- 如果换域名 / 换设备 → 在原处「导出备份」，再到新站「设置 → 导入备份」，
  选**覆盖导入**（合并模式会跳过已存在的键，看起来像"没导进去"）

## 版本管理

版本号的唯一来源是 `package.json` 的 `version`。递增规则从克制：
成块的新功能升 MINOR，其余一切（修 bug、样式、文案）升 PATCH，只改文档不升版本。
每次发版要同步改三处：`package.json`、`CHANGELOG.md`、`lib/changelog.ts`。

## 目录结构

```
app/                 页面（只做编排，不放业务 state）
  components/shell/  应用外壳：启动初始化、更新提示、导航、设置、庆祝
  components/diet/   饮食页的每张卡（一句话记、搜索、份量、概览、质量分、建议、当天列表）
  components/health/ 健康小屋的每张卡（各自管自己的 state）
  components/takeout/菜单库（含菜品营养估算与关联）
  components/today/  首页专用（含「今天吃什么」与「今天还该吃点啥」）
lib/                 纯逻辑
  storage/           数据层：键名契约、读写原语、各领域 CRUD、备份
  nutrition/         营养层：纯函数核心、查库、份量解析、目标推导、
                     质量分、建议引擎、菜单估算、推荐、今天吃什么的选择引擎
  ai/                模型那一层：DeepSeek 调用封装（浏览器直连）、
                     「帮我挑」的 prompt 组装 / 白名单 / 去数字
data/                随包分发的数据（食物库、份量表、示例菜单库等）
scripts/             图标生成、发布、子路径自检、数据兼容自检、浏览器冒烟、
                     食物库质检、营养探针、样例数据生成
  android/           装安卓 SDK、打 APK（见上面「打安卓包」）
  fixtures/          兼容样本数据（自检脚本与冒烟测试共用同一份）
android/             Capacitor 生成的安卓工程（构建产物不入库，配置入库）
capacitor.config.ts  壳的配置：appId / webDir / 桌面名
```

**一条硬规矩：页面文件保持一眼能读完。** 每张卡自己管状态、通过回调通知父级 ——
把所有状态堆在一个页面里的写法一旦铺开，改一处就要通读八百行，这个错误不重犯。

**另一条硬规矩：`lib/nutrition/` 与 `lib/ai/` 不许 import 任何 UI / Next / localStorage 的东西。**
它只接受入参、只返回结果（id 与时间戳也由调用方传进来，不在里面 `Date.now()`；
DeepSeek 的 Key 也是调用方传进去的，不在 `lib/ai/` 里读 localStorage）。
换来的是它能在 Node 里被直接调用 —— 上面那些闸门才跑得起来，
也才能对着任意一条历史记录重算一遍看对不对。

**食物库只在需要它的页面加载。** `lib/nutrition/library.ts` 会带上那份
243 条食物的 JSON，打进 chunk 后约 68KB（gzip 14KB 上下）。
目前需要它的是**饮食页、菜单库、首页的推荐**；**健康小屋与周报不需要** ——
周报的质量分只依赖记录里的营养快照，不查库。

实测（`BASE_PATH` 构建后各页面引用的 chunk 合计）：
首页 756KB / gzip 227KB、饮食页 744KB / 221KB、菜单库 721KB / 213KB，
而不带食物库的健康小屋 675KB / 205KB、周报 660KB / 200KB ——
差出来的那 20KB 左右就是它。给新页面加功能时留意别顺手 import 进来，
构建后对比一下各页面引用的 chunk 里搜不搜得到某个食物名就知道了。
